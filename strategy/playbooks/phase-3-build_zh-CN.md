# 🔨 阶段 3 剧本 — 构建与迭代

> **耗时**：2-12 周（视范围而定） | **投入智能体**：15-30+ | **门禁负责人**：智能体编排师

---

## 目标

通过持续的“开发↔QA”循环实现所有功能。每项任务在开始下一项之前都必须经过验证。这是工作量最集中的阶段，也是 NEXUS 编排能力发挥最大价值的地方。

## 前置条件

- [ ] 阶段 2 质量门禁已通过（基础已验证）
- [ ] 带有 RICE 评分的 Sprint 优先级规划师 Backlog 已就绪
- [ ] CI/CD 流水线可运行
- [ ] 设计系统和组件库已就绪
- [ ] 带有鉴权系统的 API 脚手架已就绪

## 开发↔QA 循环 — 核心机制

智能体编排师通过以下循环管理每一项任务：

```
针对 sprint_backlog 中的每一项任务（按 RICE 评分排序）：

  1. 将任务分配给合适的开发智能体 (参见分配矩阵)
  2. 开发智能体“实现”任务
  3. 测试证据采集员“测试”任务
     - 视觉截图 (桌面、平板、手机)
     - 对照验收标准进行功能验证
     - 品牌一致性检查
  4. 如果 裁定结果 == 通过 (PASS):
       标记任务完成
       进入下一项任务
     否则如果 裁定结果 == 失败 (FAIL) 且 尝试次数 < 3:
       向开发智能体发送 QA 反馈
       开发智能体修复具体问题
       返回步骤 3
     否则如果 尝试次数 >= 3:
       “升级”至智能体编排师
       编排师决定：重新分配、拆解、推迟或接受现状
  5. “更新”流水线状态报告
```

## 并行构建轨道

对于 NEXUS-Full 部署模式，四条轨道同步运行：

### 轨道 A：核心产品开发 (Core Product Development)
```
负责人：智能体编排师 (执行“开发↔QA”循环)
投入智能体：前端开发工程师、后端架构师、AI 工程师、
          移动端开发工程师、高级开发工程师
QA：测试证据采集员、API 测试工程师、测试结果分析师

Sprint 节奏：2 周一个 Sprint
每日：任务实现 + QA 验证
Sprint 结束：Sprint 演示 + 追思会
```

### 轨道 B：增长与营销筹备 (Growth & Marketing Preparation)
```
负责人：项目协调专家
投入智能体：增长黑客、内容创作者、社交媒体策略师、
          应用商店优化专家

Sprint 节奏：与轨道 A 的里程碑对齐
活动内容：
- 增长黑客 → 设计病毒循环和推荐机制
- 内容创作者 → 构建发布内容流水线
- 社交媒体策略师 → 规划跨平台营销活动
- 应用商店优化专家 → 准备商店详情（若为移动端）
```

### 轨道 C：质量与运营 (Quality & Operations)
```
负责人：智能体编排师
投入智能体：测试证据采集员、API 测试工程师、性能基准测试专家、
          工作流优化专家、实验追踪专家

持续性活动：
- 测试证据采集员 → 为每项任务提供截图 QA
- API 测试工程师 → 为每项 API 任务提供端点验证
- 性能基准测试专家 → 定期进行压力测试
- 工作流优化专家 → 识别流程改进点
- 实验追踪专家 → 为已验证的功能设置 A/B 测试
```

### 轨道 D：品牌与体验润色 (Brand & Experience Polish)
```
负责人：品牌守护者
投入智能体：UI 设计师、品牌守护者、视觉叙事师、
          创意注入师

触发式活动：
- UI 设计师 → 当 QA 识别出视觉问题时进行组件精修
- 品牌守护者 → 定期的品牌一致性审计
- 视觉叙事师 → 随着功能完成提供视觉叙事资产
- 创意注入师 → 添加微交互和惊喜时刻
```

## Sprint 执行模板

### Sprint 规划 (第 1 天)

```
Sprint 优先级规划师激活：
1. 审阅带有最新 RICE 评分的 Backlog
2. 根据团队速率选择本 Sprint 的任务
3. 将任务分配给开发智能体
4. 识别依赖关系和执行顺序
5. 设定 Sprint 目标和成功准则

产出：带有任务分配的 Sprint 计划
```

### 每日执行 (第 2 天至第 N-1 天)

```
智能体编排师管理：
1. 当前任务状态检查
2. 执行“开发↔QA”循环
3. 识别并解决阻塞项
4. 进度追踪与报告

状态报告格式：
- 今日已完成任务：[列表]
- 正在进行 QA 的任务：[列表]
- 正在开发中的任务：[列表]
- 已阻塞任务：[列表及原因]
- QA 通过率：[X/Y]
```

### Sprint 演示 (第 N 天)

```
项目协调专家组织：
1. 演示已完成的功能
2. 审阅每项任务的 QA 证据
3. 收集利益相关者反馈
4. 根据所学知识更新 Backlog

参与者：所有活跃智能体 + 利益相关者
产出：Sprint 演示总结
```

### Sprint 追思会 (Retrospective)

```
工作流优化专家组织：
1. 哪些方面做得好？
2. 哪些方面可以改进？
3. 下个 Sprint 我们将做出哪些改变？
4. 流程效率指标评估

产出：追思会行动项
```

## 编排师决策逻辑

### 任务失败处理

```
当任务未通过 QA 时：
  如果是第 1 次尝试：
    → 向开发人员发送具体的 QA 反馈
    → 开发人员“仅”修复识别出的问题
    → 重新提交 QA
    
  如果是第 2 次尝试：
    → 发送累计的 QA 反馈
    → 考虑：该开发智能体是否合适？
    → 开发人员结合更多上下文进行修复
    → 重新提交 QA
    
  如果是第 3 次尝试：
    → “升级”处理
    → 选项：
      a) 重新分配给不同的开发智能体
      b) 将任务拆解为更小的子任务
      c) 修改方案/架构
      d) 接受带有已知局限的状态 (需记录)
      e) 推迟至未来的 Sprint
    → 记录决策内容及理由
```

### 并行任务管理

```
当多个任务没有相互依赖时：
  → 同时分配给不同的开发智能体
  → 各自运行独立的“开发↔QA”循环
  → 编排师并发追踪所有循环
  → 按依赖顺序合并已完成的任务

当任务存在依赖关系时：
  → 等待依赖项通过 QA
  → 然后分配依赖的任务
  → 在交付中包含依赖项的上下文
```

## 质量门禁检查清单

| # | 准则 | 证据来源 | 状态 |
|---|-----------|----------------|--------|
| 1 | 所有 Sprint 任务通过 QA (100% 完成) | 每项任务对应的测试证据采集员截图 | ☐ |
| 2 | 所有 API 端点均已验证 | API 测试工程师回归测试报告 | ☐ |
| 3 | 性能基准达标 (P95 < 200ms) | 性能基准测试专家报告 | ☐ |
| 4 | 品牌一致性已验证 (95% 以上依从度) | 品牌守护者审计报告 | ☐ |
| 5 | 无致命 Bug (零 P0/P1 遗留) | 测试结果分析师总结 | ☐ |
| 6 | 所有验收标准均已达成 | 逐项任务核实 | ☐ |
| 7 | 所有 PR 均已完成代码审查 | Git 历史记录证据 | ☐ |

## 门禁决策

**门禁负责人**：智能体编排师

- **通过 (PASS)**：功能完整的应用 → 阶段 4 激活
- **继续 (CONTINUE)**：需要更多 Sprint → 继续阶段 3
- **升级 (ESCALATE)**：系统性问题 → 工作室制作人介入
