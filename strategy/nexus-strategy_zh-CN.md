## 1. 战略基础

### 1.1 NEXUS 解决的问题

单个智能体固然强大。但如果缺乏协调，他们会产生：
- 相互冲突的架构决策
- 各学部之间重复劳动
- 交付边界处的质量真空
- 缺乏共享的上下文或机构记忆

**NEXUS 通过定义以下内容来消除这些失败模式：**
- 每个阶段**谁**被激活
- 他们为谁产出**什么**
- 他们在**什么时候**向谁交付
- 在进入下一环节前**如何**验证质量
- 流水线中每个智能体存在的**意义**（拒绝冗员）

### 1.2 核心原则

| 原则 | 描述 |
|-----------|-------------|
| **流水线完整性** | 未通过质量门禁，不得进入下一阶段 |
| **上下文连续性** | 每次交付都携带完整的上下文 —— 严禁让智能体在无背景的情况下开始 |
| **并行执行** | 独立的流水线并发运行，以压缩时间线 |
| **证据胜于雄辩** | 所有质量评估均需提供证据，而非空头保证 |
| **快速失败，快速修复** | 每项任务在升级处理前最多重试 3 次 |
| **单一事实来源** | 维护唯一的权威规范、任务列表和架构文档 |

## 2. NEXUS 运营模型

### 2.1 七阶段流水线

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        NEXUS 流水线                                     │
│                                                                         │
│  阶段 0          阶段 1          阶段 2           阶段 3                │
│  发现 (DISCOVER) ───▶ 策略 (STRATEGIZE) ───▶ 基础 (SCAFFOLD)  ───▶ 构建 (BUILD)  │
│  情报获取        架构设计         环境搭建         开发↔QA 循环          │
│                                                                         │
│  阶段 4          阶段 5          阶段 6                                 │
│  加固 (HARDEN)  ───▶ 发布 (LAUNCH) ───▶ 运营 (OPERATE)                        │
│  质量门禁        市场准入         持续运营                               │
│                                                                         │
│  ◆ 每个阶段之间设有质量门禁                                              │
│  ◆ 阶段内设有并行轨道                                                   │
│  ◆ 每个边界处设有反馈循环                                               │
└─────────────────────────────────────────────────────────────────────────┘
```

```
                    ┌──────────────────────┐
                    │  智能体编排师         │  ◄── 流水线控制器
                    │  (特种专家)          │
                    └──────────┬───────────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
     ┌────────▼──────┐ ┌──────▼───────┐ ┌──────▼──────────┐
     │ 工作室制作人   │ │ 项目协调专家   │ │ 高级项目经理      │
     │ (投资组合管理) │ │ (项目执行)     │ │ (任务范围划定)    │
     └───────────────┘ └──────────────┘ └─────────────────┘
              │                │                │
              ▼                ▼                ▼
     ┌─────────────────────────────────────────────────┐
     │              各学部负责人 (按阶段分工)           │

### 2.3 激活模式

NEXUS 支持三种部署配置：

| 模式 | 激活智能体 | 适用场景 | 预计耗时 |
|------|--------------|----------|----------|
| **NEXUS-Full** | 全部 | 企业级产品发布，全生命周期 | 12-24 周 |
| **NEXUS-Sprint** | 15-25 个 | 功能开发，MVP 构建 | 2-6 周 |
| **NEXUS-Micro** | 5-10 个 | Bug 修复，内容活动，单一交付物 | 1-5 天 |

### 3.3 阶段 0 质量门禁

**门禁负责人**：高管摘要生成师

| 准则 | 阈值 | 所需证据 |
|-----------|-----------|-------------------|
| 市场机会已验证 | TAM > 最小可行阈值 | 趋势研究员提供的带来源报告 |
| 用户需求已确认 | ≥3 个已验证痛点 | 用户反馈分析师 + 用户体验研究员数据 |
| 合规路径清晰 | 无阻碍性合规问题 | 法律合规检查员提供的矩阵 |
| 数据基础已评估 | 关键指标已识别 | 数据分析报告员提供的审计报告 |
| 技术可行性已确认 | 技术栈已验证 | 工具评估专家提供的评估报告 |

**产出**：高管摘要（≤500 字，SCQA 格式）→ 决策：推进 / 终止 / 转型

> **目标**：在写下第一行代码前，定义我们要构建什么、如何架构以及成功的标准。

| 智能体 | 阶段角色 | 主要产出 |
|-------|--------------|----------------|

| **高级项目经理** | 需求转任务 | 全面任务列表 |
| **Sprint 优先级规划师** | 功能优先级排序 | 优先级 Backlog (RICE 评分) |
| **UX 架构师** | 技术架构 + UX 基础 | 架构规范 + CSS 设计系统 |
| **品牌守护者** | 品牌识别系统 | 品牌基础文档 |
| **后端架构师** | 系统架构设计 | 系统架构规范 |
| **AI 工程师** | AI/ML 架构（如适用） | ML 系统设计 |
| **财务追踪专员** | 预算与资源规划 | 包含 ROI 预测的财务计划 |

### 4.2 执行序列

```
步骤 1：战略框架搭建 (并行)
├── 工作室制作人 → 战略投资组合计划 (愿景、目标、ROI 目标)
├── 品牌守护者 → 品牌基础 (宗旨、价值观、视觉识别系统)
└── 财务追踪专员 → 预算框架 (资源分配、成本预测)

步骤 2：技术架构设计 (并行，在步骤 1 之后)
├── UX 架构师 → CSS 设计系统 + 布局框架 + UX 结构
├── 后端架构师 → 系统架构 (服务、数据库、API)
├── AI 工程师 → ML 架构 (模型、管道、推理策略)
└── 高级项目经理 → 任务列表 (需求转任务，确切要求)

步骤 3：优先级排序 (串行，在步骤 2 之后)
└── Sprint 优先级规划师 → 带有 Sprint 分配的 RICE 评分 Backlog
    ├── 输入：任务列表 + 架构规范 + 预算框架
    ├── 产出：带有依赖关系图的优先级 Sprint 计划
    └── 验证：工作室制作人确认战略对齐
```

### 4.3 阶段 1 质量门禁

**门禁负责人**：工作室制作人 + 生产就绪验证员 (双重签字)

| 准则 | 阈值 | 所需证据 |

## 6. 阶段 3 — 构建与迭代

> **目标**：通过持续的“开发↔QA”循环实现功能。每项任务在进入下一项前必须经过验证。这是工作量最集中的阶段。

### 6.1 开发↔QA 循环 (Dev↔QA Loop)

这是 NEXUS 的核心。智能体编排师管理着**逐项任务的质量循环**：

```
┌─────────────────────────────────────────────────────────┐
│                   开发 ↔ QA 循环                         │
│                                                          │
│  ┌──────────┐    ┌──────────┐    ┌──────────────────┐   │
│  │ 开发人员  │───▶│   证据   │───▶│     决策逻辑     │   │
```
│  │ 智能体   │    │ 采集员   │    │                   │   │
│  │           │    │ (QA)     │    │ 通过 → 下一项任务  │   │
│  │ 实现任务 N │    │ 测试     │    │ 失败 → 重试 (≤3)   │   │
│  │           │    │ 任务 N    │    │ 阻塞 → 升级处理    │   │
│  │           │◀───│          │◀───│                   │   │
│  └──────────┘    └──────────┘    └──────────────────┘   │
│       ▲                                    │             │
│       │            QA 反馈                 │             │
│       └────────────────────────────────────┘             │
│                                                          │
│  编排师追踪：尝试次数、QA 反馈、任务状态、累计质量指标        │
└─────────────────────────────────────────────────────────┘
```

### 6.2 按任务类型划分的智能体分配

| 任务类型 | 主要开发智能体 | QA 智能体 | 专项支持 |
|-----------|------------------|----------|-------------------|
| 前端 UI | 前端开发工程师 | 测试证据采集员 | UI 设计师, 创意注入师 |
| 后端 API | 后端架构师 | API 测试工程师 | 性能基准测试专家 |
| 数据库 | 后端架构师 | API 测试工程师 | 数据分析报告员 |
| 移动端 | 移动端开发工程师 | 测试证据采集员 | 用户体验研究员 |
| AI/ML 功能 | AI 工程师 | 测试结果分析师 | 数据分析报告员 |

> **目标**：最终的质量大考。生产就绪验证员默认判定为“需改进 (NEEDS WORK)” —— 你必须提供压倒性的证据来证明其生产就绪度。

### 7.2 加固序列

```
步骤 1：证据搜集 (并行)
├── 测试证据采集员 → 全套截图 (桌面、平板、手机)
├── API 测试工程师 → 完整的端点回归测试
├── 性能基准测试专家 → 10 倍预期流量下的压力测试
└── 法律合规检查员 → 最终法规审计

步骤 2：综合分析 (并行，在步骤 1 之后)
├── 测试结果分析师 → 将所有测试数据整合进质量看板
├── 工作流优化专家 → 识别残留的流程低效环节
└── 基础设施维护工程师 → 生产环境验证

步骤 3：最终裁定 (串行，在步骤 2 之后)
└── 生产就绪验证员 → 集成报告
    ├── 交叉验证之前所有的 QA 发现
    ├── 通过截图证据测试完整的用户路径
    ├── 逐项核实需求规范的落实情况
    ├── 默认结论：需改进 (NEEDS WORK)
    └── 仅在所有准则均有压倒性证据支持时判定为：就绪 (READY)
```

### 7.3 阶段 4 质量门禁 (最终门禁)

**门禁负责人**：生产就绪验证员 (唯一权威)

| 准则 | 阈值 | 所需证据 |
|-----------|-----------|-------------------|
| 用户路径完整 | 所有关键路径正常运行 | 端到端截图 |
| 跨设备一致性 | 桌面 + 平板 + 手机适配 | 响应式截图 |
| 性能认证合格 | P95 < 200ms, 可用性 > 99.9% | 压力测试结果 |
| 安全性已验证 | 零严重漏洞 | 安全扫描报告 |
| 合规性已认证 | 符合所有监管要求 | 法律合规检查员报告 |
| 规范符合度 | 100% 落实需求规范 | 逐项核实清单 |

**裁定选项**：
- **就绪 (READY)** — 准予发布（首轮通过极罕见）
- **需改进 (NEEDS WORK)** — 带着具体的修复清单回退至阶段 3（预期内的情况）
- **未就绪 (NOT READY)** — 存在重大架构问题，回退至阶段 1/2

**预期情况**：首版实现通常需要 2-3 个修订周期。B/B+ 级别的评分是正常且健康的。

## 12. 质量门禁

### 12.1 门禁概要

| 阶段切换 | 门禁名称 | 门禁负责人 | 通过准则 |
|-------|-----------|-------------|---------------|
| 0 → 1 | 发现门禁 | 高管摘要生成师 | 市场已验证，用户需求已确认，合规路径清晰 |
| 1 → 2 | 架构门禁 | 工作室制作人 + 生产就绪验证员 | 架构完整，品牌已定义，预算已批准，Sprint 计划现实可行 |
| 2 → 3 | 基础门禁 | DevOps 自动化工程师 + 测试证据采集员 | CI/CD 正常运行，骨架应用已跑通，监控已激活 |
| 3 → 4 | 功能门禁 | 智能体编排师 | 所有任务通过 QA，无致命 Bug，性能基准达标 |
| 4 → 5 | 生产门禁 | 生产就绪验证员 (唯一权威) | 用户路径完整，跨设备表现一致，安全已验证，完全符合规范 |
| 5 → 6 | 发布门禁 | 工作室制作人 + 数据分析报告员 | 部署成功，系统稳定，增长渠道已开启 |

### 12.2 门禁失败处理

```
如果门禁裁定为“失败”：
  ├── 门禁负责人产出具体的失败报告
  ├── 智能体编排师将失败项路由给对应的负责智能体
  ├── 失败项进入开发↔QA 循环 (执行阶段 3 的机制)
  ├── 升级至工作室制作人前，每个门禁最多允许 3 次重试
  └── 工作室制作人决定：修复、缩减范围或承担风险接受现状
```

## 附录 C：NEXUS 词汇表

| 术语 | 定义 |
|------|-----------|
| **NEXUS** | 策略统一的专家网络 (Network of EXperts, Unified in Strategy) |
| **质量门禁 (Quality Gate)** | 阶段切换时的强制性检查点，需基于证据的批准方可通过 |
| **开发↔QA 循环 (Dev↔QA Loop)** | 持续的开发与测试周期，每项任务必须通过 QA 才能继续 |
| **交付 (Handoff)** | 智能体之间工作产出和上下文的结构化转移 |
| **门禁负责人 (Gate Keeper)** | 拥有批准或拒绝阶段推进权限的智能体 |
| **升级处理 (Escalation)** | 在重试次数耗尽后，将阻塞的任务提交给更高级别的权限处理 |
| **NEXUS-Full** | 包含所有智能体的完整流水线激活模式 |
| **NEXUS-Sprint** | 包含 15-25 个智能体、专注于功能或 MVP 开发的流水线模式 |
| **NEXUS-Micro** | 包含 5-10 个智能体、针对特定任务的激活模式 |
| **流水线完整性 (Pipeline Integrity)** | 确保任何阶段未通过质量门禁就绝不推进的原则 |
| **上下文连续性 (Context Continuity)** | 确保每次交付都携带完整背景信息的原则 |
| **证据胜于雄辩 (Evidence Over Claims)** | 确保质量评估基于证明而非断言的原则 |
